## Recommended order

1. **A bounded sequential-versus-two-worker certificate pilot.** This is the most direct next measurement for the M5 CPU/unified-memory goal. Use already-certified inputs to isolate throughput from an unknown mathematical bound. If W3 succeeds, freeze two of its actual module source hashes; otherwise use two completed W2 modules. Freeze that choice after reading W3's receipt, not by automatic fallback at runtime. A useful candidate is the first and last module, covering distinct chunk-index extremes. Keep proof inputs, source versions, compiler options and dependency caches identical in both modes; force actual target recompilation with isolated writable outputs.

   Proposed small design: four batches of the same two modules, in S/P/P/S order (S sequential, P concurrent), eight compilations total. Reverse the sequential order in the final batch. This balances some ordering effects but does not eliminate temperature/cache/scheduling confounding. Report both repetitions, total completed work per wall second, each module's user/system/wall time and proof outcome. The prediction is a useful throughput gain; a suggested decision gate is at least 1.3x in both paired comparisons without pressure or swap growth. Failure of that gate is a valid reason not to increase worker count; no automatic third/fourth worker.

   Suggested caps for discussion: ten-minute total stage; the existing 180-second wall/150-second CPU per module, 6 GiB simultaneous aggregate owned-process RSS, warning/critical pressure stop, 256 MiB swap-growth stop, 5 GiB free disk, 512 MiB new artifacts and 10 MiB per log. Maximum two Lean workers total, including descendants. These need an exact reviewed coordinator version before agreement: the present supervisor's one-worker policy must not simply be disabled. Measure the union of live process groups without double-counting and stop both owned groups on a stage failure. Preserve independent proof outcomes and output hashes; test a failed child, missing output and monitor failure in an agreed small control stage. No machine-wide kill. A sampled group peak is not total-machine memory use, and adding separate peak values is not an aggregate measurement.

2. **A semantics-preserving early-stop checker, before paying for many more widths.** The pinned `run` advances all K levels even when `alive` is zero. Source inspection gives a simple invariant: the only update to alive is either itself or its bitwise AND with another mask, so zero remains zero for every later step. A short-circuit implementation can return true immediately at zero, provided a generic Lean proof establishes equality with the existing run for every fuel, level, arrays and parameters. This is a routine candidate equivalence, not a newly carried theorem. It should be independently read and kernel-checked before any replacement certificate is relied upon; W3 remains frozen.

   The useful compute would be a small comparison on already-certified chunks, only after that proof/interface exists. Prediction: work falls when the last survivor dies substantially before K. Can fail: late extinction gives little saving, repeated zero comparisons cost more than they save, or conversion/unfolding erases the intended shortcut. A semantic equality alone does not prove runtime improvement. Include an initially empty alive set, a one-bit live set, fuel zero, the width-boundary transition, and a case that remains nonempty through the cap; compare full state/decision outputs, not only successful final Booleans. Check the new proof's conversion path does not re-evaluate the old full computation for each chunk. No promise of a speedup or larger theorem yet.

3. **A small exact CPU-versus-Metal survivor engine pilot.** This is the best GPU candidate I see: the same Boolean anti-diagonal reconstruction over many independent lane words, with CPU scalar/bit-sliced controls. Start from 32-bit integer lane words and explicitly map every GPU word and bit to the existing lane/chunk numbering; use no floating-point arithmetic. The GPU can report extinction levels and surviving boundary words, making proposed bounds less blind. Any surviving word must be reconstructed and checked against the actual finite-support/even-time problem; a Boolean or a reconstructed boundary prefix alone is not automatically a physical counterexample. GPU output is discovery evidence; a checked Lean certificate remains the proof route.

   The first pilot should freeze a small input set spanning first/last chunks, word boundaries (31/32 and 63/64), free-pattern versus chunk-index bits, and levels on both sides of W with both parities. Compare every retained alive mask and selected anti-diagonal entries with an independent scalar engine at tiny exhaustive widths; compare complete output words with the CPU bit-sliced engine for the selected larger cases. A dropped lane, swapped bit order and premature tail constraint must cause disagreement. Include a retained-survivor case so an accidental all-zero output cannot pass. Source reading suggests the word operations can be independent, but register spilling, per-level dispatch/synchronization and memory layout could make the GPU slower; that is precisely what a pilot must distinguish.

   Before proposing caps, read Local's actual GPU identity, supported feature family, available tooling and memory baseline. Do not infer GPU cores from the CPU count. A candidate pilot would cap explicit GPU buffers conservatively (for example 256 MiB) and have a separate combined-process/system-pressure budget; buffer allocation alone is not the job's memory footprint. Freeze wall/CPU/output/disk limits and command-buffer progress/timeout behavior before execution. Measure CPU preparation, dispatch, completion wait and result access as well as GPU execution. Only consider overlapping GPU generation and CPU proof checking after both isolated pipelines have useful measured results.

## Why these before the other tempting jobs

A larger width alone multiplies the chunk count: at fixed n = 18, width 64 needs 16,384 chunks, four times width 60, before accounting for K. That does not establish a general theorem or justify an automatic next run. The full channel-width-16 certificate could improve a different mathematical bound, but its approximately 45 MB decimal literal encoding and complete physical closure checking remain a distinct implementation issue; the fast arithmetic-only receipt is not the whole theorem. Keep it as a later mathematical option, not a background load while W3 runs.

The deciding evidence is W3's actual completion or stopped receipt. A clean pass and memory headroom favor the two-worker pilot. A cost/pressure failure favors understanding the checker and its representation before concurrency. A proof rejection favors extracting and independently interpreting the failing chunk before any performance project or larger K. These are choices to agree explicitly, not automatic branches that launch jobs.

## Primary hardware guidance and its limits

Apple's [shared resource documentation](https://developer.apple.com/documentation/metal/mtlstoragemode/shared) states that CPU and GPU share access to system-memory resources but still require synchronization before the other processor accesses changed data. Unified memory does not remove completion waits or data-layout costs. Apple's [compute example](https://developer.apple.com/documentation/metal/performing-calculations-on-a-gpu) describes independent work items and pipeline-specific threadgroup limits; it does not predict acceleration for this recurrence. Its [counter guidance](https://developer.apple.com/documentation/xcode/analyzing-apple-gpu-performance-using-counter-statistics) provides GPU activity measurements; some counter captures isolate passes, so those timings must not be silently substituted for ordinary overlapping runtime. These are platform facts, not M5 measurements.

Instinct and unexpected check: the pull is toward less duplicated verified work, not just more active cores. Three niggles were checked: GPU speed alone cannot accelerate the stock Lean kernel; an early-stop equality can still trigger costly old-definition reduction; and apparent concurrency capacity cannot be inferred by summing process peaks. All three are retained as explicit design gates. My present first choice is the small two-worker pilot after W3, with early-stop semantics developed as a separate source/proof task. No new execution approved.
