Jellyfin by default doesn't offer a native method to force a transcode for good reason. Native playback is preferred where possible because it makes the most sense to avoid doing unnecessary work on the server. If the client can play it - don't bother to transcode it, becomes a simple served file copy rather than a messy compute. But i needed to force a transcode to test my interpolation. This turned out to actually be quite simple - I used a devious linux trick. I copy out the /usr/lib/jellyfin-ffmpeg/ffmpeg and mount it back as ffmpeg8 - I mount ffmpeg.sh over ffmpeg. This is a custom bash script that simply intercepts all calls to ffmpeg, lets me inspect the arguments, pass them on to ffmpeg8 if nothing needs to be done, or intercept the command completely and modify the arguments. To force a transcode I watch the specific case where the client player request a quality playback of 420 kbps - the lowest possible setting, which always forces a transcode on any content. Then, because I can modify the arguments, I scrape the important ones, inject my hardware setup, libplacebo filter and make sure the HLS flags pass through normally (The ones that make the content streamable). Because the client player is agnostic about the file it actually recieves - playback continues transparantly, running the modified command, with no further input required from the user. The GUI will report the wrong details, but the file served will be correct.

Note any of this needs a patched ffmpeg-libplacebo, but thankfully the [jellyfin-ffmpeg](https://github.com/jellyfin/jellyfin-ffmpeg) team have a very clever in-docker build script. There is already a patch against libplacebo in builder/patches/libplacebo - dropping the patch in here and running ./build trixie amd64 builds it in, although there are 2 other patches which need carfully incorporating as well. The end of this build spits out a jellyfin-ffmpeg8_8.1.2-3-trixie_amd64.deb package, which is trivial to install with apt install.

The really cool thing about this, and how it relates to testing shaders, is you can make an edit to the shader, play a file in jellyfin, force a transcode and see immediately what the changes to the shader did. A new student starting out? Write a simple inversion shader. It's so simple its on the [libplacebo manual page](https://libplacebo.org/custom-shaders/)
```
//!HOOK LUMA
//!HOOK RGB
//!BIND HOOKED

vec4 hook()
{
    vec4 color = HOOKED_texOff(0);
    color.rgb = vec3(1.0) - color.rgb;
    return color;
}
```

That's it. Write it to a file, point libplacebo=fps=24:frame_mixer=custom_n:custom_shader_path=/path/to/shader , play the file in jellyfin. Boom, see for yourself what the shader does on live content.

Ironically, this code I barely understand (But I do understand a little). There are many examples of awesome shaders on the internet. Shaders do not process (threaded) sequentially like a CPU and they do not see the whole image. They divide the image in to tiny bits, as small as a single pixel, they do a massively parallel matrix-math compute to practically ever pixel at the same time. This example shader captures a pixel, looks at it's colour, subtracts it from 1, and passes it back as the new image. All done all over the image for every pixel extremely quickly.

The power of the GPU has always been in these shaders, not in any one vendor's propriety systems and extension that provide additional functionality, or features with a dedicated hardware path to offload work from the main queue, such as Intel's low-power h264 / h265 encoding mode, which is useful, a reasonable USP, but not essential. Intel, AMD, NVIDIA, whatever. They are all the same. They all do the same thing, just with extra fluff in the offering. I am not saying one is better than the other, hardware extensions are valuable, only this is the key-fact the industry has long been ignoring. Do what you are good at first, add extra functionality later. Shader programs are the same as CPU programs, the only difference is they are much harder to read, less obvious what they do, and AI like Claude Code is extremely good at writing them. Bill Gates was right - software matters more than hardware. And he was wrong - hardware enables, supports and optimizes for the software in the first place. Hardware provides the functionality. Software implements it. It then asks for more - it would be really useful if it could do this. Hardware iterates and adds new functionality.
